# CAP의 핵심 철학

> **모델은 제안하고, 코드가 판정한다.**

CAP(Code As Planned)은 작은 로컬 모델로도 믿고 맡길 수 있는 코딩 에이전트를 목표로 한다.
모델은 다음에 할 일을 제안하고, 그 제안을 받아들일지와 일이 끝났는지는 하네스의 코드가 정한다.
아래 다섯 원칙은 새 기능을 넣을 때마다 대조하는 기준이다.

## 1. 판단은 코드가 맡는다

끝났는지, 이 파일을 바꿔도 되는지, 이 명령을 돌려도 되는지는 코드가 정한다.

- 완료 판정은 테스트 명령의 종료 코드와 출력으로 내린다 (`gate.rs`).
- 파일과 명령의 허용 여부는 권한 표가 정한다 (`perm.rs`). 키가 든 파일은 어떤 모드에서도 읽기와 쓰기를 거절한다.
- 같은 입력에는 항상 같은 판정이 나온다. 판정 규칙은 단위 테스트로 고정한다.

## 2. "됐다"는 증거로 인정한다

모델이 도구 호출 없이 글만 답하면 CAP은 그것을 "끝났다"는 주장으로 받아들이고, 곧바로 테스트를 돌린다.

- 테스트가 통과하면 `verified`.
- 테스트가 실패하면 실패 출력을 모델에게 돌려주고 계속 고치게 한다.
- 테스트가 없는 프로젝트에서 파일을 바꿨으면 `unverified`로 보고한다.
- 종료 코드도 같다. `verified`와 `answered`만 0이다.

## 3. 작은 모델의 약점은 하네스가 메운다

작은 모델이 자주 하는 실수는 모델을 탓하는 대신 하네스가 받아 준다.

- 다른 에이전트식 도구 이름과 인자 이름을 알아듣는다 (`file_path` → `path` 등).
- 깨진 인자는 어디가 틀렸는지 짚어서 돌려준다.
- 똑같이 실패한 호출을 세 번째로 보내면 실행을 건너뛰고 다른 방법을 쓰라고 답한다.
- "이제 고치겠습니다" 같은 예고 문장은 완료 주장과 구분해서, 바로 실행하라고 알려 준다.
- 빈 답과 중간에 잘린 답은 다시 시도한다.
- 도구 호출을 글자로 써서 보내는 서버의 답도 호출로 읽는다.

## 4. 모델이 쓰는 글자와 호출 횟수가 곧 비용이다

로컬 모델은 느리고 문맥이 좁다. 모델이 읽고 쓰는 양과 호출 횟수를 줄이는 것이 곧 속도다.

- 긴 명령 출력은 앞과 뒤만 남긴다.
- 문맥이 차면 오래된 도구 출력부터 한 줄 요약으로 바꾼다 (`context.rs`).
- 바뀌지 않은 파일을 다시 읽으면 내용 대신 "이미 갖고 있다"고 답한다.
- 방금 통과한 테스트 결과는 파일이 바뀌기 전까지 다시 쓴다.

## 5. 근거가 있는 것만 넣고 한 것만 말한다

- 기능은 그 동작을 보여 주는 테스트와 함께 들어간다.
- 문서와 변경 기록에는 실제로 돌려 본 것과 그 숫자만 적는다. 단위 테스트로만 확인한 것은 그렇게 적는다.
- 다른 에이전트보다 낫다는 말은 같은 모델, 같은 과제, 같은 채점으로 잰 뒤에 한다.
